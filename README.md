# p1-w1-d3-t1 · Первый запрос: fetch и промис

> Тип: крепкая (fetch, then/catch/finally) · Репозиторий: один отдельный

> Подключить `.js` к HTML через `<script>`, отсмотреть в браузере. Сегодня только промисы — `async/await` будет завтра, его не используем.

## Задача

Первый настоящий поход в сеть. `fetch` — встроенная функция браузера, которая отправляет HTTP-запрос и **сразу** возвращает промис. Важно понять, что именно в этом промисе: не данные, а объект ответа (`response`) — статус, заголовки и тело, которое ещё нужно прочитать. Сегодня разбираешься с полным циклом запроса и учишься не проглядеть ошибки.

```
fetch — запрос к серверу, возвращает промис
┌──────────────────────────────────────────────────────┐
│ fetch(url) → промис с ОТВЕТОМ (не с данными)         │
│ res.ok — проверить самой: 404/500 не отклоняют fetch │
│ res.json() — тоже промис (тело читается асинхронно)  │
│ .then цепочкой · .catch на всю цепь · .finally убрать│
└──────────────────────────────────────────────────────┘
спиннер → запрос → данные/ошибка → спиннер убрать
```

## Что такое fetch (прочитай перед началом)

- `fetch(url)` отправляет GET-запрос и возвращает промис. Промис появляется мгновенно, данные — позже.
- Промис исполняется объектом `response`. Это ещё **не** данные: в нём `status` (200, 404, 500…), `ok` (`true`, если статус 200–299) и тело.
- **Ловушка:** `fetch` отклоняется только когда запрос вообще не состоялся (нет сети, неверный домен). На ответ 404 или 500 он **не** отклоняется — промис успешен, просто `ok === false`. Значит статус проверяешь сама и сама бросаешь ошибку, если он не тот.
- Тело читается асинхронно: `response.json()` тоже возвращает промис, который исполнится уже распарсенными данными. Поэтому его результат либо возвращают из `.then` (тогда следующий `.then` дождётся), либо обрабатывают дальше по цепочке.
- `.catch` в конце ловит ошибку любого звена цепочки; `.finally` выполняется в любом случае — там убирают индикатор загрузки.

## API для работы (без ключей и регистрации)

Публичный тестовый API: **`https://jsonplaceholder.typicode.com`** — отдаёт фейковые, но реалистичные данные по GET.

Доступные ресурсы: `/users`, `/posts`, `/comments`, `/todos`, `/albums`, `/photos`.

Примеры адресов:
- `https://jsonplaceholder.typicode.com/users` — список пользователей
- `https://jsonplaceholder.typicode.com/users/1` — один пользователь
- `https://jsonplaceholder.typicode.com/posts?userId=1` — посты конкретного пользователя (фильтр)
- `https://jsonplaceholder.typicode.com/posts/1/comments` — комментарии к посту (вложенный ресурс)
- `https://jsonplaceholder.typicode.com/posts/99999` — **несуществующий** id: вернёт 404, пригодится для проверки ошибок

## Что нужно сделать (по релизам)

**Release 1 — запрос и вывод.** По кнопке запросить одного пользователя и вывести его данные в `#card` (имя, email, город — посмотри структуру ответа сама). Перед запросом показать «Загрузка…» в `#status`, после — убрать. Цепочка: `fetch` → прочитать тело → отрисовать. Данные выводить безопасно (`textContent`).

**Release 2 — ошибки как надо.** Вторая кнопка запрашивает несуществующий ресурс (id вне набора → 404). Показать, что цепочка при этом **не** попадает в `.catch` сама: добавить проверку статуса ответа и бросить ошибку, если он неуспешный — только тогда управление уйдёт в `.catch`, где показать понятное сообщение в `#status`. Убедиться, что уборка индикатора работает в обоих исходах (успех и ошибка) — это место для `.finally`.

**Release 3 — состояния и разбор.** Сделать три видимых состояния интерфейса: загрузка, успех, ошибка (разные классы/цвета). Пока идёт запрос — кнопки заблокированы, потом снова активны (в любом исходе). В `NOTES.md` ответить: что лежит в промисе, который вернул `fetch`; почему 404 не отклоняет промис; зачем чтение тела — отдельный промис; чем `.finally` удобнее, чем дублировать уборку в `.then` и `.catch`.

## Ожидаемый результат

- По первой кнопке карточка заполняется данными пользователя с сервера; во время запроса виден индикатор загрузки, после — исчезает.
- По второй кнопке приходит неуспешный статус, и благодаря собственной проверке управление уходит в обработчик ошибки: пользователь видит понятное сообщение, а не пустую карточку и не «успех» с пустыми данными.
- Индикатор снимается и кнопки разблокируются в обоих случаях; в `NOTES.md` разобрано устройство запроса.

## Критерии приёмки

* Запрос через `fetch`, цепочка `.then`, ошибка обрабатывается в `.catch`, уборка — в `.finally`.
* Статус ответа проверяется явно, при неуспешном — бросается ошибка (иначе 404 «проедет» как успех); это продемонстрировано второй кнопкой.
* Есть три состояния (загрузка/успех/ошибка), кнопки блокируются на время запроса; вывод через `textContent`.
* В `NOTES.md` объяснено: что в промисе от `fetch`, почему 404 не отклоняет его, зачем `.json()` — отдельный промис.
